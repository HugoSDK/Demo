O(log n)

Each step throws away half of what's left: 16 → 8 → 4 → 2 → 1. That's log₂(n) steps. A billion items? About 30 comparisons. That is the power of halving — and why search engines and databases live on it.

Step 6 of 6 — Your Turn & The Traps

Where it goes wrong.

The algorithm is short, which is exactly why it bites you. One quick prediction first, then the four classic traps that catch everyone — and a bug to spot.

YOU TRY Predict the first move

The list has 15 items (indices 0–14). We search for 80.

arr[mid] = 41, target = 80 → keep which half?

TRAP 1 It must be sorted

Binary search assumes order. On an unsorted list it throws away the wrong half and misses items that are sitting right there.

TRAP 2 <= not <

The loop is while low <= high. Use < and you skip the final one-element window — so a value sitting alone at low == high never gets checked.

low, high = 4, 4 # one item left while low < high: # False! never checks arr[4] while low <= high: # correct — checks it

TRAP 3 Move past mid

You must use mid + 1 / mid - 1. Reassigning low = mid (not mid + 1) can leave the range the same size forever → infinite loop.

low = mid # range may never shrink 💀 low = mid + 1 # guaranteed progress ✓

TRAP 4 Computing mid

Use integer division: (low + high) // 2. Python's ints are unbounded so you're safe — but in Java/C, low + high can overflow, so the pro habit is low + (high - low) // 2.

mid = (low + high) // 2 # fine in Python mid = low + (high - low) // 2 # overflow-safe everywhere

SPOT THE BUG One line is wrong

def search(arr, t): low, high = 0, len(arr) - 1 while low < high: # line A mid = (low + high) // 2 # line B if arr[mid] == t: return mid elif arr[mid] < t: low = mid + 1 # line C else: high = mid - 1 # line D return -1
RECAP

O(1) directory (instant, needs labels) → O(n) linear (simple, slow) → O(log n) binary (fast, needs a sorted list). Same problem, three trade-offs. Next lesson: how do we get the list sorted in the first place? And — this halving idea is just recursion in disguise.
